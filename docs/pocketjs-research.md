# PocketJS research for CPZeroJS

Research snapshot: 2026-09-27. Sources were read from the public `pocket-nexus/pocketjs` GitHub repository, including the checked-out source at its current `main` tip. Cargo metadata in the checkout identifies the repository as `pocket-stack/pocketjs`; GitHub currently serves the requested `pocket-nexus` URL.

## What PocketJS actually is

PocketJS is a substantially broader runtime than CPZeroJS: its TypeScript framework adapters (Solid, Vue Vapor, and Octane) write mutations into a native retained UI tree; a QuickJS guest drives a Rust core that owns flex layout, styles, animations, and draw-list generation. Its README describes that pipeline and its fixed subset of build-time baked utility styles ([README](https://github.com/pocket-nexus/pocketjs/blob/main/README.md)). The source confirms a platform-neutral retained UI core and explicit tree/tick invariants ([core `lib.rs`](https://github.com/pocket-nexus/pocketjs/blob/main/engine/core/src/lib.rs)); the QuickJS C runtime registers a large explicit operation table for tree, style, text, animation, input and other host calls ([`pocket_runtime.c`](https://github.com/pocket-nexus/pocketjs/blob/main/engine/quickjs-c/pocket_runtime.c)).

This is not a drop-in framework for CPZeroJS. PocketJS's guest/framework calls its own operation protocol and depends on the Rust `pocketjs-core` retained tree and draw pipeline. CPZeroJS's contract instead maps a small `__cp` API to LVGL 9 widgets and uses LVGL flex layout/rendering. Adopting `@pocketjs/framework` alone would not connect those systems; adopting the engine would replace core UI/layout/rendering decisions and add a sizable Rust and host integration project ([implementation contract](implementation-contract.md), [PocketJS engine workspace](https://github.com/pocket-nexus/pocketjs/blob/main/engine/Cargo.toml)).

## Patterns worth borrowing

- **Make each UI update a deterministic transaction.** PocketJS defines one frame call as an uninterruptible transaction, queues asynchronous completions to frame boundaries, and advances timers on a logical clock. Its core documents one fixed step per tick and byte-exact frame goldens ([README, frame contract](https://github.com/pocket-nexus/pocketjs/blob/main/README.md#the-frame-contract), [core `lib.rs`](https://github.com/pocket-nexus/pocketjs/blob/main/engine/core/src/lib.rs)). CPZero already has `__cpTick(nowMs)` and drains Promise jobs after native callbacks. Keep that one well-defined turn boundary; consider queued external completions and a fixed-step test clock if async timing starts making behavior hard to reproduce.
- **Treat the JS/native boundary as a versioned contract.** PocketJS keeps operation IDs and payload semantics in shared contracts/spec files, and its C runtime translates those operations explicitly ([contracts](https://github.com/pocket-nexus/pocketjs/tree/main/contracts/spec), [runtime](https://github.com/pocket-nexus/pocketjs/blob/main/engine/quickjs-c/pocket_runtime.c)). CPZero's `__cp` API is already deliberately small. As it grows, document accepted props/events, error behavior, ownership and lifecycle in one contract and keep the TS wrapper and C host aligned; avoid letting framework internals leak into the bridge.
- **Keep work off the per-frame JS path when it can be declarative.** PocketJS compiles fixed class literals and animation timelines into tables consumed by its core ([README, styling and animation](https://github.com/pocket-nexus/pocketjs/blob/main/README.md#styling)). CPZero can borrow the constraint, not the Tailwind surface: keep styling a bounded set of typed LVGL props, and only move repeated static work into build-time data if profiling justifies it.
- **Make target support explicit as it grows.** PocketJS apps declare required capabilities and a target profile must satisfy them before packaging ([manifest spec](https://github.com/pocket-nexus/pocketjs/blob/main/contracts/spec/pocket-manifest.ts), [platform registry](https://github.com/pocket-nexus/pocketjs/blob/main/contracts/spec/platforms.ts)). CPZero currently has an SDL simulator and a packaging helper that expects a separately built ARM64 Linux host; a small capability manifest could later prevent an app from silently assuming an input or service a target does not offer. This is a later-stage idea, not a need for v0.1.
- **Give stale handles safe behavior.** PocketJS tags reused node slots with generations so old handles cannot accidentally point at a new node ([core `lib.rs`](https://github.com/pocket-nexus/pocketjs/blob/main/engine/core/src/lib.rs)). CPZero currently specifies monotonically increasing native IDs, which avoids reuse in its initial design. If it later reuses IDs or introduces asynchronous references, generation-tagged handles are a useful guard.

## Recommendation

Keep CPZeroJS's thin TypeScript SDK over QuickJS and LVGL. PocketJS validates the broad direction—TypeScript guest code, QuickJS, a narrow native boundary and native rendering—but its runtime is a different retained renderer with much broader product scope. Borrow the deterministic turn/frame discipline and contract-first boundary now; consider explicit target capabilities and stale-handle generations only when CPZero's features make them useful. Do not add PocketJS as a runtime dependency.
